開発メモ

判定ロジックをなぜこの形にしたか、実データで何を確認したか、どこで間違えたかの記録。仕様を変えるときは、まずここを読んでください。

2026-09 ／ 検証データ: n025-034.pdf（10p・210×210mm）, 01-16_.pdf（16p・182×257mm）

1. 何を解決するツールか

見開きレイアウトのInDesignから単ページ書き出ししたPDFは、ノド側の断ち代に隣ページの絵柄が入ります。通常の面付では折られて隠れるため問題になりませんが、リング綴じのように折らずに4方断裁してペラで丁合する製本では、ノド側にも正しい断ち代が必要です。

当初の要件は「ノド側を白にする」「絵柄を左右反転して足す」の2択でしたが、実データを通すうちに見開きでつながっている絵柄はそのまま残すべきという第3の選択肢が必要だとわかり、さらに1ページの中で上下に処理を分ける必要も出てきました。

2. 判定ロジックの根拠

2-1. 絵柄の有無は「色の濃さ」ではなく「真っ白かどうか」で見る

なぜそうしたか
最初はインク量（255からの差が12以上の画素の割合）で絵柄の有無を判定していました。これだと色の薄い写真が紙地と区別できません。実データのp2では、ノド際が淡い白壁の写真で、紙地と誤判定されていました。
調べると、写真は淡くても真っ白（255,255,255）にはならず、紙地は必ず真っ白になります。実データで、写真側は真っ白が0.0%、紙地側は98.3%と、はっきり分かれました。
注意：白い画像（スキャンした白背景など）が置かれている場合は、この判定では紙地と区別できません。そのときは手動で指定してください。しきい値は詳細設定の「紙地とみなす明るさ」（既定253）で調整できます。

2-2. サンプリングは仕上がり線から0.25mm離す

なぜそうしたか
当初0.06mm離して測っていましたが、これは走査解像度で1画素未満です。仕上がり線上のアンチエイリアス1画素を「絵柄あり」と拾ってしまい、断ち代が白なのに「両側に絵柄」と誤判定していました。0.25mmまで離すと確実に1画素以上になり、解消しました。

2-3. 断ち代の「奥まで」絵柄が続いているかを見る

なぜそうしたか
仕上がり線の際だけを見て「そのまま」にすると、斜めの帯で白い楔が残ります。帯は仕上がり線上にはあっても、断ち代の奥へ行くと上下にずれて、そこは隣ページの白紙だからです。「そのまま」はその白紙ごと温存してしまいます。
そこで、行ごとに断ち代3mm全体を調べ、紙地が50%以上を占める行は「そのまま」にせずミラーにします。写真の飛んだハイライト（真っ白になる）で誤判定しないよう、全画素一致ではなく割合で見ています。

2-4. 色の食い違いは「局所の変化との比」で見る

なぜそうしたか
両側に絵柄があっても、別々の写真が隣り合っているだけの場合はミラーが正しい。しかし固定のしきい値では分離できませんでした。見開きでつながっている写真でも、継ぎ目で色が食い違うことが実際にあるためです（n025-034のp5で色差58）。
決め手は比率でした。別写真が隣接している箇所（01-16_のp12下半分）は色差74.5に対して局所の変化0.5＝149倍。つながっている写真（p5）は色差58に対して局所の変化6.0＝9.7倍。
そこで、仕上がり線をまたぐ色差を、同じ側の内部での色の変化と比べ、色差 > max(25, 局所の変化×14 + 10) ならミラーにします。ディテールの多い写真ほどしきい値が自動的に緩みます。

2-5. 「そのまま」はまとまった範囲にだけ使う

なぜそうしたか
行ごとに素直に判定すると、白地ページを横切る細い帯（4mm程度）だけが「そのまま」になります。これは一見正しそうですが、帯の周囲に隣ページの絵柄が中途半端に残り、かえって不安定でした。
そこで、ページ高さの20%以上まとまっている「そのまま」だけを採用し、短いものはミラーに倒します。絵柄はあるので白にはしません。逆に、「そのまま」に挟まれた短いミラーは「そのまま」に吸収します（写真の飛んだ白などで面が細切れになるのを防ぐため）。白に隣接する短いミラーは残します（紙地の面に入った帯は反転させたいため）。

2-6. ミラーの帯は上下に広げる

なぜそうしたか
斜めの帯をミラーする場合、帯の厚み分だけの範囲で切ると、断ち代の奥でずれた分が覆えず反転した絵柄が途切れます。そこでミラーの帯を上下に断ち代の3倍（9mm）広げます。紙地を反転しても紙地のままなので、白の区間に食い込んでも害はありません。「そのまま」の区間に隣接するときは、そちらを上書きしないよう広げません。

2-7. 走査の仕様（まとめ）

解像度ページ高さを400分割（A5で約0.5mm刻み）。走査倍率は辺の長さから5〜10倍で自動決定。
測る位置仕上がり線から0.25mm離し、0.15mm厚の帯を内外に3本ずつ。色の比較は長手方向に1mmの移動平均をかけてから。
最小区間ページ高さの1%。それ未満の区間は隣に吸収。
間引き判定済みの行だけで先に多数決（半径3バケット）を取り、そのあと紙地の行を最も近い判定で埋める。順序が逆だと1バケットの誤判定が広範囲に伝播します。

4. 見つけたバグと原因

1　ページ一覧が10ページまでしか表示されない
原因：スクロール領域に min-height:0 が抜けていた。flexboxでは flex:1 を指定しても min-height の初期値が auto（＝中身の高さ）なので、要素は中身の高さまで膨らみ、パネルの外にはみ出して下が切れる。overflow-y:auto はコンテナが中身より小さいときにしか効かないので、スクロールも機能しない。
なぜ見逃したか：DOM上は全ページ分の行が存在していたため、行数を数えるテストでは検出できなかった。10ページなら高さが収まって問題が出ず、16ページで初めて露見した。「ページ数が増えたときだけ起きる」という手がかりを読み違え、キャッシュの問題だと誤診した。
2　ドロップすると同じファイルが2つ読み込まれる
原因：ドロップゾーンと document の両方にドロップハンドラを付けており、イベントが親へ伝播して2回処理されていた。ゾーン側で stopPropagation() し、document 側は画面外に落とされたときだけ拾う担当に分離した。
3　走査処理の関数が丸ごと消えていた
原因：コードを範囲置換した際、隣接する関数を巻き込んで削除した。自動判定が一切動かず、結果が全てフォールバックに落ちていた。
なぜ見逃したか：テストが走査結果を直接注入していたため、その関数を一度も呼ばない経路を通っていた。
対策：インラインスクリプト内で呼ばれている関数名を全て拾い、定義が存在しないものを検出する静的チェックを追加。走査を素通しで実行するテストも追加した。

5. 出力の仕組み

  • 元PDFのバイト列は一切書き換えず、末尾に増分更新として追記する。OutputIntent・XMP・ID・Infoは無傷で、PDF/X-4のまま保たれる。
  • 白は 0 0 0 0 k（ExtGStateでOP/op false）。ミラーは、そのページの内容を複製したフォームXObjectを、仕上がり線を軸とした反転行列 -1 0 0 1 2x₀ 0 ＋クリップで重ねる。画像の再サンプリングや再圧縮は起きない。
  • 反転軸は「なじませ」分（既定0.05mm）だけ内側にずらす。軸ちょうどだと仕上がり線上に毛抜き合わせの継ぎ目が出るため。軸を内側にずらしても参照元は必ず自ページ側なので、隣の絵柄は拾わない。
  • 「ノド断ち代」というOCGレイヤーに入れる。/Usage /Print /PrintState /ON と /AS [/Print] を付け、PDF/X-4が許容する形にしている。
  • 取り消しは追記部分の切り捨てで、元ファイルとバイト単位で一致する。
  • 天地への延長は既定で断ち代と同値（3mm）。InDesignのトンボオフセットが3mmなら、角の断ち代を埋めてもトンボ線に掛からない。

6. 検証に使ったテスト

開発時に用意したもの。仕様変更時はこれらを再実行すること。

画面jsdomでページ全体を読み込み、初期化→ファイル読込→走査→実行→ページ操作→表示切替→リセットまで通しで実行し、エラーが出ないこと。
静的インラインスクリプトの構文チェック、参照している要素IDの存在確認、未定義関数の呼び出し検出。

7. 今後の課題

  • 行単位の限界。現在の処理は水平な帯の集まりなので、斜めの絵柄では境界が階段状になります。断ち代の中だけの話なので実害は出ませんが、画素単位のマスク（PDFのソフトマスク）にすれば正確に扱えます。斜めの帯も文字も、紙地の部分だけを正確に埋められます。
  • フィードバックの到達確認。送信は mode:'no-cors' のため、GAS側が受け取れていなくてもブラウザ側では検知できず、画面には「送信しました」と出ます。確実に確認するにはスプレッドシート側を見るしかありません。
  • 白い画像の扱い。紙地の判定を「真っ白かどうか」で行っているため、白背景の画像が置かれている場合は区別できません。
